  ### 4. Código Corrigido

  O arquivo app.py foi refatorado aplicando as melhores práticas de Defesa em Profundidade:
  1. Prepared Statements (Consultas Parametrizadas): Uso do placeholder ? do driver sqlite3, garantindo que o banco
  trate as variáveis estritamente como literais de dados e nunca como comandos executáveis.
  2. Armazenamento Criptográfico de Senhas: Validação usando PBKDF2 com Salt e comparação em tempo constante (hmac.
  compare_digest) para prevenir Timing Attacks.
  3. Gerenciamento Seguro de Recursos: Uso de context manager (with sqlite3.connect(...)) para assegurar o fechamento
  correto de conexões.

    import sqlite3
    import hmac
    import hashlib

    def verificar_senha(senha_fornecida: str, hash_armazenado: str, salt: bytes) -> bool:
        """Verifica a senha usando PBKDF2 em tempo constante."""
        hash_calculado = hashlib.pbkdf2_hmac(
            'sha256',
            senha_fornecida.encode('utf-8'),
            salt,
            iterations=100_000
        ).hex()
        return hmac.compare_digest(hash_calculado, hash_armazenado)

    def fazer_login(usuario: str, senha: str) -> str:
        """
        Realiza a autenticação de forma segura:
        1. Utiliza consultas parametrizadas (Prepared Statements) para prevenir SQL Injection.
        2. Utiliza context manager para fechamento seguro dos recursos.
        3. Valida credenciais comparando hashes criptográficos com salt.
        """
        with sqlite3.connect('banco_de_dados.db') as conexao:
            cursor = conexao.cursor()

            # Consulta parametrizada com placeholder '?' (mitiga SQL Injection)
            query = "SELECT password_hash, salt FROM usuarios WHERE username = ?"
            cursor.execute(query, (usuario,))
            resultado = cursor.fetchone()

        if resultado:
            hash_armazenado, salt = resultado
            if isinstance(salt, str):
                salt = bytes.fromhex(salt)

            if verificar_senha(senha, hash_armazenado, salt):
                return "Acesso Permitido!"

        return "Acesso Negado."

  Vamos organizar o raciocínio em etapas:
  ──────
  ### 1. O que já sabemos

  • Finalidade: Ambiente de laboratório/estudos hospedando uma aplicação web.
  • Exposição: Está diretamente acessível pela internet (qualquer pessoa ou bot pode alcançar o endereço IP).
  • Ponto de Gestão: Acesso administrativo remoto disponível via SSH.
  • Estado Atual: Sem anomalias ou alertas reportados; o objetivo é diagnóstico preventivo (hardening ou endurecimento de segurança).
  ──────
  ### 2. O que ainda precisamos descobrir

  Para entender a superfície de ataque (ou seja, por onde alguém poderia tentar interagir com a máquina), precisamos responder a três perguntas:

  1. Quais portas estão "ouvindo" a internet? Além do SSH e do site, há bancos de dados ou outros serviços expostos sem necessidade?
  2. Como o SSH está protegido? Ele aceita login direto como root? Usa senha simples ou autenticação por chave criptográfica?
  3. Qual é o estado de atualização do Ubuntu? O sistema e o servidor web possuem correções de segurança em dia?
  ──────
  ### 3. As três primeiras verificações defensivas

  Em uma análise inicial, nós não tentamos "invadir" nada. Nós apenas conferimos o básico da casa: se as portas e janelas estão trancadas.

  #### Verificação 1: Mapear portas e serviços escutando a rede

  • O que é: Verificar quais programas estão ativos aguardando conexões vindas da internet (por exemplo, na porta 80/443 para o site ou 22 para o SSH).
  • Por que fazer: Se você instalou um banco de dados de testes (como MySQL ou Redis) e ele estiver acessível para o mundo todo em vez de apenas localmente, qualquer pessoa
  na internet poderá tentar se conectar a ele. A regra de ouro é: fechar tudo o que não precisa estar público.

  #### Verificação 2: Revisar a blindagem do SSH

  • O que é: Avaliar as configurações do serviço de acesso remoto (/etc/ssh/sshd_config).
  • Por que fazer: Todo servidor público na internet recebe tentativas diárias automatizadas de adivinhação de senhas (brute force). Se o usuário administrador (root) puder
  entrar diretamente com uma senha comum, o risco é alto. Em segurança, a recomendação padrão é desativar o login por senha e usar chaves SSH, além de restringir o login
  direto do root.

  #### Verificação 3: Checar o status de atualizações do sistema

  • O que é: Consultar o gerenciador de pacotes do Ubuntu para ver se há pacotes com atualizações de segurança pendentes.
  • Por que fazer: Softwares conhecidos (como Apache, Nginx ou o próprio kernel do Linux) recebem correções frequentes para falhas descobertas pela comunidade. Manter os
  pacotes atualizados elimina a imensa maioria dos ataques automatizados que exploram versões antigas.
  ──────
